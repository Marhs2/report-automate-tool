# 로컬 LLM 모델 선정 근거 및 추출 정확도 자체 평가

일일보고 자동 구조화(프로젝트명 / 완료 업무 / 진행 중 업무 / 이슈 / 협조 요청 / 다음 계획 추출)에
사용할 로컬 모델을 고르기 위해, 개발 PC에 설치된 후보 모델 7종을 동일 조건에서 비교했다.

- 측정일: 2026-07-30
- 대상: LM Studio에 로드 가능한 로컬 GGUF 모델 7종 (외부 API 호출 없음, 오프라인 동작)
- 데이터: 자체 작성 정답 데이터셋 32건 (`benchmark/dataset/gold_dataset.json`)
- 실행: 추론(reasoning) 설정 3가지 조건에서 총 641회 호출 (조건별 원시 응답 전량 보존)

## 1. 결론

**qwen3.5-4b를 추론(reasoning) 최대 설정으로 사용하는 것을 권장한다. micro F1 88.9%로 2위와 9.8%p 차이가 난다.**

| 구분 | 모델 / 설정 | micro F1 | 보고 1건 처리 | 근거 |
|---|---|---|---|---|
| **채택** | **qwen3.5-4b + `reasoning_effort=high`** | **88.9%** | 평균 69초 | 전 항목 최고. 프로젝트 F1 95.5%, 협조 요청 90.9%, 다음 계획 95.5% |
| 대안 (속도) | qwen3.5-4b + `reasoning_effort=none` | 72.2% | 평균 1.3초 | 즉시 응답이 필요할 때. 정확도 16.7%p 손실 |
| 대안 (균형) | google/gemma-4-e2b + `high` | 79.1% | 평균 10.7초 | 추론 켠 상태에서 속도·정확도 균형이 가장 좋음 |
| 대안 | nuextract3 + `high` | 77.1% | 평균 10.2초 | 추론 끈 상태(75.5%)에서는 1위였으나 추론 이득이 가장 작음 |
| 탈락 | nvidia/nemotron-3-nano-4b | 71.6% | 평균 8.6초 | 메신저체 보고에서 29.9%로 급락 |
| 탈락 | kanana-2-3b-instruct-i1 | 44.4% | 평균 1.2초 | 추론 미지원. 이슈 항목 F1 20.4%로 사실상 이슈 분류 불가 |
| 탈락 | lfm2.5-8b-a1b | 25.9% | 평균 13.5초 | 복수 프로젝트 보고 20건 중 13건을 한 덩어리로 병합 |
| 측정 중단 | minicpm5-1b | - | 1건에 30초 + 로딩 108초 | 5.2k 토큰을 사고하고도 프롬프트 예시를 그대로 베껌. 3절 참고 |

품질 요구사항인 "보고 1건 구조화 10분 이내"는 최악 케이스(qwen3.5-4b high, 131초)에도 여유가 크다.
따라서 속도보다 정확도를 택하는 것이 맞다.

정확도 88.9%는 항목 132개 중 약 15개를 틀린다는 뜻이므로, **사용자 확인·수정 단계(사용 흐름 ②)는
선택이 아니라 필수**다. 원문 보존과 화면 수정 기능이 모델 정확도보다 중요한 안전장치다.

### 백엔드에 반영해야 할 호출 설정

```python
# 필수 3종 세트. 하나라도 빠지면 정확도나 성공률이 크게 떨어진다.
response_format = {"type": "json_schema", "json_schema": {...}}  # JSON 파싱 실패 0%
reasoning_effort = "high"                                        # 정확도 +16.7%p
max_tokens = 16384                                               # 사고 과정 분량 확보
```

그리고 **LM Studio 모델을 `--parallel 1 --context-length 32768` 로 로드해야 한다.** 4절 참고.

## 4. 중요 발견: `--parallel 4` 때문에 추론 모드가 통째로 실패했다

첫 실행은 LM Studio 기본값(추론 on, max_tokens 1536)으로 돌렸는데 결과가 무너졌다.
qwen3.5-4b는 32건 전부 JSON을 한 글자도 출력하지 못했다(JSON 유효율 0%).

원인 추적 과정은 이렇다.

1. 응답의 `finish_reason`이 항상 `length`이고 `content`는 빈 문자열, `reasoning_content`에만
   1만 자 넘는 사고 과정이 담겨 있었다. 사고만 하다 토큰이 끊긴 것이다.
2. `max_tokens`를 8192, 16384로 올려도 **완료 토큰이 정확히 3,020개에서 멈췄다.**
   상한을 올려도 값이 변하지 않으니 max_tokens 문제가 아니다.
3. `lms ps`로 보니 모델이 `CONTEXT 8192, PARALLEL 4`로 로드되어 있었다.
   프롬프트 5,172 토큰 + 생성 3,020 토큰 = **정확히 8,192**.
4. `--context-length 32768`로 올려도 3,020에서 그대로 멈췄다. **컨텍스트가 parallel 슬롯 수만큼
   분할되기 때문이다** (32768 / 4 = 8192).
5. `--parallel 1 --context-length 32768`로 로드하자 사고를 끝까지 마치고 정상 JSON을 출력했다.

즉 "소형 모델은 추론을 켜면 JSON을 못 만든다"는 1차 결론은 **런타임 설정 오류였다.**
설정을 고친 뒤에는 추론을 켠 쪽이 모든 모델에서 더 정확하다.

| 모델 | ① 추론 on, ctx 8192/parallel 4 | ② 추론 off | ③ 추론 high, ctx 32768/parallel 1 |
|---|---|---|---|
| qwen3.5-4b | JSON 유효 **0%** / 23.2초 | 72.2% / 1.3초 | **88.9%** / 69.1초 |
| google/gemma-4-e2b | 72.1% (JSON 78.1%) / 11.5초 | 73.7% / 2.3초 | **79.1%** / 10.7초 |
| nuextract3 | 71.2% / 10.2초 | 75.5% / 2.3초 | **77.1%** / 10.2초 |
| nvidia/nemotron-3-nano-4b | 72.0% (JSON 90.6%) / 9.0초 | 66.7% / 2.1초 | **71.6%** / 8.6초 |
| lfm2.5-8b-a1b | 9.5% (JSON 46.9%) / 7.7초 | 20.7% / 9.7초 | **25.9%** / 13.5초 |
| kanana-2-3b-instruct-i1 | 45.1% / 1.2초 | 44.8% / 1.3초 | 44.4% / 1.2초 |

kanana는 추론을 지원하지 않아 세 조건이 오차 범위 내로 동일하다(44.4~45.1%). 이는 대조군 역할을 한다.

1차 실행 결과는 `benchmark/results/raw_run1_thinking_on/`, `run1_tables.md`에 보존했다.
단, 1차 실행의 minicpm5-1b 0%는 모델 문제가 아니라 폴백 로직이 LM Studio가 지원하지 않는
`response_format: json_object`를 보낸 하네스 버그였고 이후 수정했다.

## 6. 채점 방법

문자열 완전 일치로 채점하면 표현만 다른 정답이 전부 오답이 되므로, 다음 규칙으로 항목 단위 매칭을 했다.

1. **프로젝트 매칭** — 공백·기호 제거 정규화 후 별칭 병합(`A사 MES 구축` → `A사 MES` 등). 완전 일치를
   먼저 짝지고, 남은 것은 유사도 0.6 이상에서 매칭.
2. **항목 매칭** — 매칭된 프로젝트 안에서 필드별로 문자 bigram Dice 유사도 0.5 이상이면 정탐(TP).
   유사도 높은 쌍부터 탐욕적으로 1:1 배정.
3. 매칭 실패한 정답 프로젝트의 항목은 전부 미탐(FN), 없는 프로젝트를 만들어낸 경우 그 항목은 전부 오탐(FP).
4. 지표: 필드별 정밀도/재현율/F1, 전체 micro F1(항목 수 가중), macro F1(필드 평균),
   이슈 `status` 정확도, 빈 보고 처리 정확도, JSON 유효율, 스키마 준수율, 지연시간.

이 지표는 **보수적(하한)** 이다. 예를 들어 `monitoring dashboard 알림 규칙 설정 완료`를
`모니터링 대시보드 알림 규칙 설정`으로 옮긴 사례는 의미상 정답이지만 음차 표기 때문에 오답으로 계산된다.
모든 모델에 동일하게 적용되므로 순위 비교에는 영향이 없다.

"~부탁드립니다"가 협조 요청인지 다음 계획인지, "원인 확인 필요"가 이슈인지 진행 중 업무인지 같은
**판단이 필요한 분류에서 사고 과정이 실제로 효과를 낸다.** 단순 복사에 가까운 완료 업무는 이득이 거의 없다.

이슈 상태(해결/미해결) 판정은 매칭된 이슈에 대해 전 모델 100%다. 미해결 이슈 구분 표시 요구사항은 안전하다.

**빈 보고 처리는 추론을 켜면 오히려 나빠진다.** 업무가 없는 인사말 보고(D16)에서 qwen3.5-4b와
nuextract3은 빈 배열 대신 항목을 만들었다.

```
입력: 안녕하세요. 오늘은 종일 사내 정보보안 교육 참석했습니다. 특별한 이슈 없습니다.
qwen3.5-4b(high): projectName="미분류 프로젝트", completedTasks=["사내 정보보안 교육 참석"]
```

없는 내용을 지어낸 것은 아니고, 교육 참석을 업무로 볼지에 대한 판단 차이다(정답 라벨은 프로젝트 업무가
아니므로 제외). 다만 추론을 켜면 "무엇이든 찾아내려는" 경향이 생기는 것은 사실이므로, 프롬프트에
프로젝트 업무가 아닌 활동(교육·휴가·행정)의 처리 기준을 명시할 필요가 있다.

|---|---|---|---|---|---|
| 표 | 2 | 100.0% | 100.0% | 100.0% | 87.5% |

**메신저체가 유일한 취약점이고, 여기서 모델 격차가 가장 크다.** qwen3.5-4b는 71.4%인데
나머지는 16.7~29.9%로 무너진다. 이 항목 하나가 qwen3.5-4b를 채택하는 실질적 이유다.
반면 추론을 끈 조건에서는 영문 혼합이 32.2%로 약점이었는데, 추론을 켜면 94.4%로 해결된다.

그래도 최악 131초로 요구사항 상한 10분의 22% 수준이다. 팀원이 하루 한 번 제출하는 사용 패턴이라
**1~2분 대기는 수용 가능**하다고 판단했다. 화면에는 진행 표시를 두고 비동기로 처리하면 된다.

즉시 응답이 필요하면 gemma-4-e2b(10.7초, 79.1%)가 현실적인 타협점이다.

## 8. 실패 유형 집계

`benchmark/results/reasoning_high_failmodes.md`

| 모델 | 복수 프로젝트를<br>하나로 병합 | 프로젝트<br>전부 오인 | 미분류로<br>떠넘김 | 빈 결과 | 파싱 실패 | 프롬프트<br>예시 오염 | 출력 항목 수<br>(정답 132) |
|---|---|---|---|---|---|---|---|
| qwen3.5-4b | 1 | 1 | 3 | 0 | 0 | 0 | 129 |
| nvidia/nemotron-3-nano-4b | 0 | 2 | 4 | 0 | 0 | 0 | 136 |
| google/gemma-4-e2b | 0 | 4 | 6 | 0 | 0 | 0 | 131 |
| nuextract3 | 0 | 3 | 8 | 0 | 0 | 0 | 135 |
| kanana-2-3b-instruct-i1 | 8 | 5 | 5 | 0 | 0 | 0 | 129 |
| lfm2.5-8b-a1b | 13 | 8 | 7 | 5 | 0 | 2 | 84 |

("복수 프로젝트를 하나로 병합"의 분모는 정답이 2개 이상 프로젝트인 20건, 나머지는 32건)

추론을 켜면 **프로젝트 분리 능력이 극적으로 개선된다.** qwen3.5-4b는 병합 실패가 8건 → 1건,
gemma-4-e2b는 6건 → 0건, nuextract3은 1건 → 0건이다. "프로젝트별로 분리" 요구사항은
사고 과정 없이는 소형 모델에게 어려운 작업이라는 뜻이다.

남은 오류 유형은 세 가지다.

1. **프로젝트명 오인 (메신저체)** — 본문에 프로젝트명이 없고 기능명만 있으면 기능명을 프로젝트로 만든다.
   D22에서 qwen3.5-4b도 `여우비` 대신 `마이페이지`를 프로젝트로 출력했다(항목 내용은 4개 모두 정확).
   → 완화책: 알려진 프로젝트 목록을 프롬프트에 주입하고, 프로젝트 별칭(alias) 매핑으로 사후 병합.
   DB에 이미 `project_aliases` 테이블이 있으므로 이를 프롬프트에 넣으면 된다.
2. **미분류로 떠넘김** — 프로젝트 귀속이 애매하면 `미분류 프로젝트`로 보낸다. qwen3.5-4b 3건,
   nuextract3 8건. 화면에서 사용자가 재지정할 수 있으면 실무상 큰 문제는 아니다.
3. **프로젝트 업무가 아닌 활동 처리 기준 부재** — 교육·행정 활동을 업무로 볼지 모델마다 다르다(7.2 참고).

프롬프트 개선 후보: 알려진 프로젝트 목록·별칭 주입, 프로젝트명이 본문에 없을 때의 추론 지침,
비업무 활동(교육·휴가) 처리 기준 명시.

## 9. 재현 방법

```bash
# 1) LM Studio를 켜고 로컬 서버를 127.0.0.1:1234 로 실행

# 2) 추론 최대 조건 (권장 설정). --preload 가 lms CLI로 parallel=1 로드까지 수행한다
python benchmark/run_benchmark.py --reasoning high --max-tokens 16384 \
    --preload --context-length 32768 --parallel 1 \
    --out-dir benchmark/results/raw_reasoning_high

# 추론 끄기 조건 (비교군)
python benchmark/run_benchmark.py

# 특정 모델만 / 기존 결과 무시하고 재실행
python benchmark/run_benchmark.py qwen3.5-4b
python benchmark/run_benchmark.py --force

# 3) 채점 → <prefix>scores.json, summary.csv, tables.md
python benchmark/score_benchmark.py --raw-dir benchmark/results/raw_reasoning_high \
    --prefix reasoning_high_

# 4) 오차 정성 분석
python benchmark/error_report.py --raw-dir=benchmark/results/raw_reasoning_high \
    --prefix=reasoning_high_
# 특정 모델·케이스 직접 비교
python benchmark/error_report.py --raw-dir=benchmark/results/raw_reasoning_high qwen3.5-4b D16 D22

# 5) 실패 유형 집계
python benchmark/failmode_report.py --raw-dir benchmark/results/raw_reasoning_high \
    --prefix reasoning_high_
```

원시 응답이 파일로 남으므로 채점 기준을 바꿔도 모델을 다시 호출할 필요가 없다.
중간에 끊겨도 같은 명령을 다시 실행하면 남은 케이스만 이어서 처리한다.

## 10. 한계

- 정답 데이터셋을 도구 개발자가 직접 작성해 라벨링 편향이 있을 수 있다. 실제 팀원 보고로 재검증이 필요하다.
- 케이스 32건, 정답 항목 132개 규모에서 micro F1 1~3%p 차이는 유의하지 않다.
  2~3위(79.1% / 77.1%)는 동급으로 보아야 한다. 다만 1위와 2위의 9.8%p 차이는 유의하다고 판단했다.
- 각 모델·케이스를 1회만 호출했다(temperature 0.1). 동일 입력 반복 시의 편차는 측정하지 않았다.
- 유사도 기반 채점이라 음차 표기·과도한 요약은 의미가 맞아도 오답으로 계산된다. 실제 체감 정확도는
  표의 수치보다 다소 높다.
- minicpm5-1b는 추론 최대 조건에서 32건을 완주하지 않았다(1건만 측정 후 중단). 추론 끄기 조건의
  최하위 성적(15.8%)과 1건 결과를 근거로 제외했다.
- `reasoning_effort` 중간값(`low`, `medium`)은 전체 32건으로 측정하지 않았다. 단건 탐색에서는
  `high`와 사고 토큰 수가 비슷했다(3.3k~6.8k).
- 주간보고 생성(`weekly_prompt.txt`) 품질은 이 평가 범위에 없다. 별도 평가가 필요하다.
